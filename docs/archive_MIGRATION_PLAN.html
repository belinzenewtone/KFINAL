LifeOS → Jetpack Compose Migration Plan
Migration Blueprint · 2026

LifeOS → Jetpack Compose

Full Android rewrite: 47 screens, 10 stores, 15 database tables. 1:1 UI fidelity — every animation, every colour, every touch interaction reproduced in Compose. The Kotlin SMS parser ships untouched.

47 screens ~32 k TS → Kotlin SMS parser: zero changes ~20–22 weeks total Android-only target
Decision Log
Why not Flutter

Flutter adds Dart as a third language. The SMS parser is Kotlin; bridging it through platform channels would add complexity, not remove it. Every screen rewritten in Dart is a screen that could instead be written in the same language as the parser.

Why not Compose Multiplatform

The app has zero iOS-specific features. The SMS pipeline is Android-only and always will be. "Multiplatform" adds a shared-module split and commonMain/androidMain indirection with no user-facing payoff. Target: Jetpack Compose (Android), same Gradle project that already hosts the parser.

What is kept verbatim

The entire modules/lifeos-sms/ directory — all 24 Kotlin files, all 5 test files, all WorkManager workers, the BroadcastReceiver, the SQLite writer, the parser pipeline. The Compose app becomes the UI shell around a parser that already exists and already works.

Database continuity

Both the existing SMS parser and the new Compose UI will share the same lifeos.db file using WAL mode — exactly as the current RN app does today. No migration scripts, no data loss. Room is configured to open the same file path the parser's DbWriter.kt already writes to.

RN ComponentCompose approachCritical detail

GlassCard — Compose structure

@Composable
fun GlassCard(
    variant: GlassVariant = GlassVariant.Default,
    onClick: (() -> Unit)? = null,
    content: @Composable () -> Unit
) {
    val gradient = Brush.linearGradient(
        colors = listOf(Color(0xFF101014), Color(0xFF0E1B2E), Color(0xFF101014)),
        start = Offset(0f, 0f), end = Offset(1f, 1f)  // direction (0,0)→(1,1)
    )
    Box(
        Modifier
            .clip(RoundedCornerShape(20.dp))          // borderRadius.lg
            .background(gradient)
            .drawBehind {
                // tint overlay: accent → primary22, else rgba(30,35,45,.55)
                drawRect(color = tintColor, blendMode = BlendMode.SrcOver)
                // frost film
                drawRect(color = Color(0x74141C1C))
                // hairline border (drawn as inner stroke)
                drawRoundRect(color = Color(0x14FFFFFF), style = Stroke(1.dp.toPx()), …)
            }
            .then(if (onClick != null) Modifier.clickable(onClick = onClick) else Modifier)
    ) { content() }
}

01
Foundation — Gradle, Room, Hilt, Theme
Weeks 1–3 · ~3 weeks

Set up the Compose project skeleton inside the existing Android module. Nothing user-visible yet — this phase is the plumbing that everything else depends on.

  • Add Compose BOM, Navigation-Compose, Hilt, Room, DataStore, Vico to app/build.gradle
  • Create LifeOsDatabase as a Room @Database opening lifeos.db with .setJournalMode(WAL) — same file path as DbWriter.kt
  • Define all 15 Room @Entity classes, matching every column, index, and constraint from schema.ts exactly
  • Write all DAOs with @Querys covering every query in the 13 TS repository classes
  • Create LifeOsTheme composable: darkColorScheme() and lightColorScheme() using the token values from paperTheme.ts
  • Port all typography values to Typography object (30/24/20/18/16/15sp, weights 700/600/500/400)
  • Port all spacing, radius, and motion tokens to a Dimens / Motion Kotlin object
  • Set up Hilt AppModule providing the Room database, repositories, and DataStore
  • Wire DataStore Preferences to mirror all fields in AppSettings + UserProfile
Critical — database file path

The parser's DbWriter.kt calls context.getDatabasePath("lifeos.db"). Room must open the exact same path: Room.databaseBuilder(context, LifeOsDatabase::class.java, "lifeos.db"). No rename, no copy.

02
Design System — All shared components
Weeks 4–5 · ~2 weeks

Build every shared composable before touching any screen. Screens composed from verified primitives stay consistent automatically.

  • GlassCard — 3 variants (default, elevated, accent), layered Box + LinearGradient brush + drawBehind overlays
  • FrostCard — 2 glow variants (blue, teal), 3 stacked Canvas glow rings at exact pixel offsets
  • FloatingTabBar — absolutely positioned, 58dp height, 24dp radius, spring animation on scale + pill opacity
  • PageScaffold — TopAppBar (52dp), back action, eyebrow/title/subtitle, actions slot, scrollable/fixed toggle
  • HeroSurface — bottom-only 28dp radius, gradient + frost overlay, leading/action/footer slots
  • ShimmerLoadingState — InfiniteTransition, alpha 0.35↔0.85, 900ms, all rows in unison
  • TopBanner — AnimatedVisibility, zIndex 50, 4 tones, enter 220ms / exit 180ms
  • InlineBanner — static, 3 tones, icon + text + optional trailing
  • SectionHeader — label + optional action (TouchableRipple → clickable)
  • TransactionListItem — category icon, merchant, amount, date, status chip
  • MetricCard — FrostCard wrapper, label + headlineMedium amount
  • All Chip, Dropdown, SearchFilterBar equivalents

06
AssistantEngine — Port to Kotlin
Week 17 · ~1 week

The TS AssistantEngine is a pure keyword-router + SQLite engine with no external API calls. It ports to Kotlin with minimal friction since the SQL already runs on the same Room database.

  • Port all 19 intent handlers as Kotlin suspend funs, calling Room DAOs directly
  • Port extractPeriod() and extractCategory() string matchers exactly (same keyword lists)
  • Port follow-up resolution (prefix detection + recursive re-run with no history)
  • Port the top-merchant raw SQL query as a Room @RawQuery
  • Port ASCII progress bar rendering (█░) for goals output
  • Wire to AssistantViewModel: user message → engine → Room save → UI update
No LLM involved

The Anthropic SDK listed in package.json as a dev dependency is never called at runtime. The engine is entirely local. No API key needed in the Compose app.

07
SMS Module Wiring
Week 18 · ~1 week

The SMS module exposes its API through the Expo Modules system, which is a React Native bridge. In the Compose app, you call the underlying Kotlin classes directly — no bridge needed.

  • Call SmsReceiverModule's Kotlin methods directly from SmsViewModel (no bridge layer)
  • Register SmsReceiver BroadcastReceiver in the app's AndroidManifest.xml (already done in the module's manifest)
  • Replace onNewTransaction JS event with a Room Flow on the transactions table — the DbWriter.kt inserts into the same Room-managed database, so changes propagate automatically
  • Replace onFulizaLimitNeeded JS event with a LocalBroadcastManager or EventBus internal to the app
  • Port app-startup calls: enableBackgroundReceiver, setFulizaLimit, ensureIngestSweep to direct Kotlin calls in Application.onCreate()
  • Replace foreground WAL checkpoint (PRAGMA wal_checkpoint(FULL)) with Room's built-in WAL management — Room handles this natively
Important

Because the Compose app and the SMS parser share the same Room database instance (via Hilt singleton), the DbWriter.kt in the parser must be updated to use the same Room SupportSQLiteDatabase connection rather than opening its own raw SQLite connection. This is the one change required to the SMS module — but it is internal only (no public API change) and eliminates the need for WAL checkpointing entirely.

08
1:1 Polish & Verification
Weeks 19–22 · ~4 weeks

Go screen by screen with the RN app running side-by-side. Measure, compare, fix. This phase is as long as it needs to be.

  • Animation timing: record both apps at 60fps, compare frame-by-frame for spring curves and duration
  • Haptic feedback: HapticFeedbackConstants.VIRTUAL_KEY (light) and LONG_PRESS (warning) mapping to all existing haptic call sites
  • Dark / light theme: verify every surface, every text role, every border on both themes
  • Category color palette: all 14 hex values used for chart coloring, icons, and progress bars
  • Bottom safe area: verify 100dp bottom padding on every scrollable screen
  • FloatingTabBar spring: A/B the spring curve against the original until visually identical
  • SMS import state machine: verify all 7 actions and all phase transitions in ImportSmsSheet
  • Budget alert logic: verify alert threshold tiers (high 90%, medium 75%, low 50%) and the firedBudgetAlerts dedup logic
  • Fuliza limit flow: reproduce the onFulizaLimitNeeded dialog path end-to-end
  • Offline behavior: all screens must function with no network (app is 100% offline-first)
Risk Register
RiskSeverityMitigation
DbWriter.kt uses raw SQLite connection alongside Room HIGH Phase 7 change: pass Room's SupportSQLiteDatabase into DbWriter. Eliminates dual-connection conflict entirely. This is the only SMS-module code change.
Room entity schema drift from actual lifeos.db HIGH In Phase 1, dump the live schema with PRAGMA table_info for all 15 tables and validate every Room entity against it before writing any screen.
Glassmorphism visual drift (no native blur) MED The RN version uses no native blur either — all opacity layers. The Compose Canvas drawBehind approach produces identical output. Record both at 4K and compare.
FloatingTabBar spring feels different MED The RN spring (friction=7, tension=90) maps approximately to Compose spring(dampingRatio=0.43f, stiffness=375f). Fine-tune in Phase 8 with side-by-side 120fps comparison.
Paging 3 API differences vs. manual offset pagination MED The RN app uses manual offset pagination (page size 50, offset integer). Implement the same pattern first with a manual offset DAO query; migrate to Paging 3 only if needed.
Recurring event expansion performance LOW The TS version caps at 400 iterations and 366-day spans. Port the same caps. Run on a background coroutine via Dispatchers.IO.
CSV import (PapaParse → JVM CSV lib) LOW OpenCSV handles all formats PapaParse covers. The CSV import is a relatively small, self-contained screen.
Final Note

The most important constraint in this migration is the database. Get Phase 1 right — particularly the Room entity schema and WAL configuration — and the rest follows naturally. Every other challenge in this plan is well-understood Compose work. The parser, which is the actual hard part of this app, ships on day one exactly as it is today.
